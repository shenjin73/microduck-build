# A. 发给供应商的问题清单（HD-1910-C001）

> 已从资料图确认的**不用再问**：型号 `HD-1910-C001`、TTL 三线串行总线、电压 `4–8.4V`、
> 堵转 `9kg·cm@4.8V / 12kg·cm@6V`、空载速度 `0.139/0.111 s/60°`、堵转电流
> `1.2A@4.8V / 1.5A@6V`、额定电流 `500/690mA`、重量 `21±2g`、尺寸 `34×20×23mm`、
> PA+Fiber 外壳、双轴金属齿轮。
>
> **缺的是「怎么跟它说话」——协议与寄存器。** 这是 A 部分的全部内容。

## A1. 协议与物理层（5 项）

> 已核实的官方 runtime 事实（供对照）：
> `microduck/duck-control/src/model.rs:12` `NUM_JOINTS = 15`、`:31` `MOUTH_INDEX = 9`、
> `:78` `IMU_DXL_ID = 200`、`:80` `BAUD_RATE = 1_000_000`；
> `bus.rs:18` `use rustypot::servo::dynamixel::xl330::Xl330Controller`、`:27` `READ_ADDR = 124`；
> `deploy/robotd.toml:19` `port = "/dev/ttyS2"`。
>
> **这就是 HD-1910 必须对齐的靶子。**

| # | 问题 | 为什么需要 | 通过标准 |
|---|---|---|---|
| A1.1 | 通信协议是什么？是否为 **Dynamixel Protocol 2.0**？若不是，是 Feetech 自有协议还是别的？给出完整协议文档 | 官方 runtime（`microduck/duck-control/src/bus.rs:18`）写死 `rustypot` 的 `Xl330Controller` + Dynamixel P2。**协议不对，现有 runtime 一行都用不了** | 能拿到**完整协议规范**；或能用 `rustypot` 直接读写（最理想） |
| A1.2 | 波特率范围？是否支持 **1 Mbaud**？ | 官方 runtime 用 `1_000_000` baud（`model.rs:80`；`:91` 注释「3 = 1 Mbps, must agree with BAUD_RATE」） | 支持 1M baud 且稳定 |
| A1.3 | 半双工 UART 的**电气电平**（3.3V / 5V）与**方向控制方式**（自动收发 / 需 GPIO 控制 DE 脚）？ | 决定连接板硬件设计。方向控制方式影响 Linux UART 驱动与抖动 | 电平与主板 IO 兼容；方向控制可确定实现 |

## A2. 寄存器表（6 项）

| # | 问题 | 为什么需要 | 通过标准 |
|---|---|---|---|
| A2.1 | 完整**寄存器地址表**：地址、长度、读写权限、单位、范围、默认值 | runtime 的 `FeetechIo`/`Hd1910Io` 要逐寄存器实现；BAM 辨识也要写 goal position / 读状态 | 拿到完整表；关键寄存器地址可验证 |
| A2.2 | **位置**寄存器：地址、单位（0–4095 计数 / 0–360°）、分辨率（bit）、零点定义、是否支持多圈 | 直接映射到 obs 的 `joint_pos` 与 action target | 分辨率 ≥ 12 bit；每关节可校准到 Microduck 的 `DEFAULT_POSITION` |
| A2.3 | **速度**寄存器：地址、单位（rad/s / step/s / rpm）、是否可读实际速度 | 进入 obs 的 `joint_vel` | 换算误差 < 5–10%，否则要加 DR 或重训 |
| A2.4 | **P / I / D 增益**寄存器：地址、单位、范围、**固件控制律语义**（是否 `PWM = kp × error / divisor`，divisor 是多少） | BAM 控制律依赖固件 kp；仿真必须复现它。XL330 对应 `kp_fw=200.0`、divisor 256、PWM limit 885 | 可写、可读、可复现；I/D 可置 0 或可建模 |
| A2.5 | **最大 PWM / 力矩限制 / 电流限制**寄存器：是否存在？默认值？可写范围？ | BAM 用 `1.75A` 固件限流算可持续扭矩（`kt×1.75A≈0.6405 Nm`）。不知道限流就算不出真实能力 | 有明确限流值且可配置 |
| A2.6 | **加速度 / 目标速度限制 / 内部平滑**：是否存在？`q_target` 是否被内部速率限制？ | BAM 的 STS3215 actuator 有 `q_target_smooth = clamp(q_target, prev ± max_velocity·dt)`。**若 HD-1910 也有，仿真必须模拟，否则控制律是错的** | 明确回答有/无；若有，给出限速参数 |

# B. 自查决策项

这 5 项不需要问别人，是你自己的选择。每项都给出「选项 → 解锁什么 / 代价是什么」。

## B1. 主板型号

| 选项 | 解锁 | 代价 |
|---|---|---|
| **A. 沿用 Radxa Zero 3W / RK3566**（推荐） | 官方 runtime 的 board-specific 工作全部复用：UART overlay、NPU overlay、Rockchip MPP、GStreamer、ONNX Runtime、systemd units | 需确认供应与价格 |
| B. 其他 Linux ARM 板（保留 UART/CSI/NPU/VPU） | 灵活性 | 重做全部 deploy scripts；CSI/NPU 驱动可能要自己搞 |
| C. ESP32/MCU + 外置 AI 板 | — | 需重写 runtime 架构，**不建议第一版** |

**需要确认的**：具体型号、是否有 **CSI、NPU/VPU、可用 UART（含 DMA）、Linux 支持程度**。

> 风险计划 §R5 的判断：换主板的代价远大于换电机——因为 runtime 里有大量 board-specific 工作。

## B2. 连接板目标

| 选项 | 说明 |
|---|---|
| **A. 复刻原 Microduck HAT** | 电路已知、风险最低；但需原板资料（可能拿不到） |
| **B. 自己设计电源 + 总线 + IMU/ToF 连接板** | 可控；但必须保障 15 舵机的**供电瞬态**与半双工 UART 1Mbps 稳定性 |

**设计时必须满足**（来自风险计划 §R5）：

- 15 个舵机供电瞬态（额定总电流可达 **10A 级**，`690mA×15`；峰值更高 → 线径/铜箔/电容要按峰值设计）
- 半双工 UART 1 Mbps 稳定（含方向控制时序）
- IMU 更新时间与坐标系
- ONNX 推理**不抢占** 50 Hz 控制回路
- 热管理

## B3. 第一版行为目标（MVP）

计划建议的 MVP（**建议采纳**）：

- [ ] 能站立
- [ ] 能被 gamepad/命令控制前后左右
- [ ] 摔倒后低风险恢复，或至少 limp
- [ ] 能 OTA/ssh 部署新 policy
- [ ] **不强求** soccer / tidy / autonomous vision

**如果第一版就要 camera/ToF/自主行为**：风险计划 §R6 标为「中高风险」——`mediad`/`tofd`/NPU/
camera calibration 全是 board-specific 陷阱，且 `docs/camera-hardware.md` 显示仅 FOV/分辨率/
畸变就能显著影响 tidy/soccer 行为。建议先做机械预留 + 软件 stub。

## B4. 训练资源

**已在 Week 0.5 用数字定案**（见 `apple-silicon-throughput-benchmark.md`），所以这项现在只是选择：

| 路线 | 成本 | 3.9 亿步耗时 | 定位 |
|---|---:|---:|---|
| **A. 云 NVIDIA + 官方 `microduck_rl`** | ~$2–4 / 次 | ~1.5 h | 保真度基准 |
| **B. Mac + `microduck_local` 过夜** | 电费 ~0 | ~5.8 h | 零成本 MVP |

**建议：先 B 后 A。** B 路需先补 3 个 obs 级 DR 缺口（IMU 安装误差 ±6°、编码器 bias
±0.015 rad、IMU 延迟 0–1 步）。注意两栈 step 数**不等价**（batch 差 12 倍）。

## B5. 是否保持 15 舵机（mouth 不进 policy）

**建议保持**：真机 runtime 是 15 个舵机（`model.rs:12` `NUM_JOINTS = 15`），但
**policy action 只有 14 维，`MOUTH_INDEX = 9` 不在其中**（`model.rs:31`）。这是 61→14 contract
的一部分，改了就要改 policy 接口——**风险计划 §R7 明令不要动**。

- 关节限位不同 → 必须更新 XML + runtime clamp

# D. 这些答案分别解锁什么

| 答案 | 解锁 | 没答案会怎样 |
|---|---|---|
| **A1.1 协议文档** | Week 1 单电机 spike → Week 3 BAM 辨识 → Week 6 `FeetechIo` | **全流程阻塞**；不知协议连一个电机都驱动不了 |

| A2.4 P 增益语义 | BAM `kp_fw` 标定 | 仿真与真机行为不匹配 |
| A2.6 内部速率限制 | actuator 模型正确性 | 控制律是错的（仍在模仿 XL330） |
| B1 主板 | Week 6 runtime 适配范围 | 无法估工时 |
